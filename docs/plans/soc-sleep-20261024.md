**No vlow/vmin entry is observed in the measured prefix. Whether either state
was entered later in the 23-minute quiet interval is unknown.** Do not turn
missing after-counters into a whole-window negative result. Nor does changing
the observation time explain away the initial zeros: RPM count/accumulated
duration are cumulative; an earlier entry should remain visible after resume.

There were two concrete logging defects:

1. `sleep 60` measures awake monotonic time. It is frozen with the phone and
   can need many minutes of boot time to finish. The old loop then exited on
   its deadline without taking another snapshot.
2. AWK buffered four RPM records into one `/dev/kmsg` write. The persistent
   logger retained them as a line containing literal `\\x0a` separators.
   `extract.py` selected only its last A9 tag, dropping Count and both timestamp
   fields. Replaying with the repair recovers all16 RPM fields across the two
   samples: all are genuinely0. The earlier UNAVAILABLE entry verdict becomes
   NO_INCREMENT for this limited sample window.

## Implemented observation change

`scripts/mainline/android/gnss-outdoor-fix4/resume-stats.c` is a small static
ARM64 reader. The sleep job takes its baseline before releasing the existing
test wake locks, then runs this reader as a foreground child in the same mount
namespace and owner. The existing release/reacquire and cleanup paths remain.

The reader waits on absolute **CLOCK_BOOTTIME** deadlines one second apart.
This clock includes suspend, so an expired wait returns promptly once the task
can run after thaw. It detects suspend through the increase in BOOTTIME minus
MONOTONIC, or an increase in the kernel suspend-success counter. It reads
vlow/vmin immediately in that iteration, before the slow shell wake-source
inventory. It also samples every60 boot-time seconds when awake, and samples
on a resume that has already crossed the capture deadline. The shell then
reacquires its existing test wake lock and takes a final full snapshot.

This is a **non-waking** observer: no RTC/wakealarm, alarm-clock timer, new wake
lock, CPU-idle setting, or firmware request. BOOTTIME includes suspended time;
the separate BOOTTIME_ALARM timer class is what can wake the system. See the
[Linux clock_nanosleep API](https://man7.org/linux/man-pages/man2/clock_nanosleep.2.html)
and [timer clock definitions](https://man7.org/linux/man-pages/man2/timer_create.2.html).

The native reader preserves integer64 fields and adds the firmware Client Votes
mask as a numeric diagnostic. Each record uses its own kmsg write. The shell's
RPM writer also closes each record separately; extraction recovers older
escaped-newline records without decoding arbitrary raw logs. Missing/malformed
RPM records remain unavailable, rather than fabricated zero measurements.
`onb.py` pushes/chmods the built helper along with the existing sleep scripts.

**Observation limit:** this is post-thaw userspace sampling, not a hard kernel
PM callback. The normal 108–319s sleeps make its wait overdue at resume; actual
scheduling latency still needs measuring on the phone. Very short cycles or
multiple cycles before it is scheduled can coalesce; `resume_cycles` and the
PM log expose that limitation. A success-counter update may also arrive after
the clock jump, so resume-labelled records are observations, not an exact
transition count. No assertion that it captured all13 historical transitions
is made. If a future run shows missed wakes, add a small **read-only**
`qcom_stats` PM notifier snapshot at PREPARE/POST_SUSPEND; POST also fires on
failed suspend, so pair it with suspend result evidence. The
[kernel notifier contract](https://docs.kernel.org/driver-api/pm/notifiers.html)
defines those semantics. Do not create periodic RTC wakeups to improve the
apparent sample count or interpret induced wakes as natural sleep behavior.

python3 -B scripts/mainline/android/gnss-outdoor-fix4/test-resume-stats.py

## Why current s2idle is not proof of SoC collapse

Actual integ7 config has `CONFIG_CPU_IDLE=y`, **ARM_PSCI_CPUIDLE unset**, and
`CONFIG_SUSPEND=y`; its boot command line includes `cpuidle.off=1`,
`clk_ignore_unused`, `pd_ignore_unused`, `regulator_ignore_unused`.
`qcom_stats`, DEBUG_FS and SMEM are built in and both files were readable.

The local7.2.10 source is decisive:

- `kernel/sched/idle.c:cpuidle_idle_call()` takes the default idle path when
  cpuidle is unavailable, before its special s2idle path.
- `arch/arm64/kernel/idle.c:arch_cpu_idle()` calls `cpu_do_idle()` and WFI.
- `drivers/cpuidle/cpuidle-psci.c` is the code that would enter firmware
  CPU_SUSPEND and suspend/resume CPU genpd domains during s2idle. It is absent
  from this image. Removing the command-line token alone cannot add it.

Thus this image demonstrates frozen Android/devices plus WFI, and does not
request PSCI CPU power-collapse through that driver. Whether other retained
resources also block RPM sleep remains unresolved. Generic s2idle permits the
deepest **available** CPU idle state; it does not supply missing platform
collapse support. See [kernel system sleep states](https://docs.kernel.org/admin-guide/pm/sleep-states.html)
and [CPU idle management](https://docs.kernel.org/admin-guide/pm/cpuidle.html).

## Concrete change sequence, not applied in this delivery

1. **Repair observation first, preserve the working image.** Run the new
   logger on the same integ7-class kernel with no power-policy change. Require
   a same-boot baseline and final RPM snapshot, retain all PM events, and
   compare resume samples with those events. Judge Android logical suspend,
   CPU collapse, RPM mode entry and measured drain separately. For RPM entry,
   report per-mode Count_delta and duration_ticks_delta/19200000, with coverage;
   positive cumulative count/duration is evidence, absence of a source is not0.

2. **Build CPU-only PSCI on the current working kernel.** Enable
   `CONFIG_ARM_PSCI_CPUIDLE=y` and `CONFIG_ARM_PSCI_CPUIDLE_DOMAIN=y` with their
   normal Kconfig dependencies; remove the single `cpuidle.off=1` token.
   Keep all8 CPU nodes, native CPU-PC state parameters and OSI CPU-domain
   topology, while leaving both cluster `domain-idle-states` lists absent,
   as in the earlier C1 CPU-only control. Verify the actual packed DT has that
   topology; do not assume the old DT or kernel is interchangeable. Preserve
   the current wrapped storage, FP6/FP7 QSEE, media, audio and UART fixes.
   Build from a frozen current parent in private objects, obtain native
   generated symbol CRCs, and check every packaged module against them;
   rebuild affected modules rather than copying/patching old CRC tables.
   ABL-check the final boot with its matching neutral DTBO.

   First establish boot/OSI and normal CPU-PC entry, then repeat the same
   quiet s2idle window with the new observer. Capture normal cpuidle usage/time,
   rejected counts and **s2idle/usage + s2idle/time** for each core, plus RPM
   counters. They use different accounting paths. CPU-PC working with RPM
   still flat is a useful partial result, not a SoC-collapse pass.

3. **Add cluster entry independently.** Use the already proposed/native
   silver-only GDHS state0x40000022 first; keep gold and cluster-PC unselected.
   If stable, add gold GDHS separately. The earlier C2 reset warrants this
   smaller sequence. Do not restore both clusters' full PC lists and remove
   resource-vote guards in one test. No guessed stock system-PC parameter or
   inert `qcom,notify-rpm` DT property implements the stock coordination code.

4. **Resolve actual retained votes or missing system coordination.** If both
   clusters enter and RPM stays flat, collect read-only clock/regulator/genpd
   summaries and named RPM master counters where available (APSS, MPSS, ADSP,
   CDSP, TZ). Preserve raw data privately and reduce it to public labels/masks.
   The current generic client-vote mask has no verified bit-name map: do not
   label a bit USB/XO from its number alone. Adjust one identified unclaimed
   clock/domain/regulator handoff at a time; keep unrelated ignore-unused
   flags. An RPM-master reader/binding addition, if needed, is a separate
   read-only observability change, not a whole-SoC power request.

5. **Assess PSCI SYSTEM_SUSPEND/`deep` as a separate candidate.** The current
   upstream `drivers/firmware/psci/psci.c:psci_init_system_suspend()` registers
   suspend-to-RAM ops only when PSCI_FEATURES(SYSTEM_SUSPEND) is not reported
   unsupported. Firmware version alone does not establish the feature, and
   the saved boot84 capture does not establish a usable `deep` entry in
   `/sys/power/mem_sleep`. Have the phone owner capture that read-only fact.
   If `deep` is absent, forcing `mem_sleep_default=deep` or inventing a PSCI
   call does not supply support. If present, first do one short controlled
   transition using the existing known wake source, with the new counters and
   persistent logs. It is separate from s2idle plus PSCI CPU_SUSPEND. Stock's
   qcom lpm-levels/system-PC path also does not prove support for the distinct
   PSCI SYSTEM_SUSPEND call.

For each future candidate the owning coordinator retains recovery and phone
authority. The boot deadline is disarmed after boot admission and the ordinary
watchdog can stop in suspend; neither guarantees recovery from a new deep
state hang. No new trial is authorized/executed by this host delivery. The
next accepted result must combine resume health, interval coverage and RPM
evidence; use a matched unplugged stock window and battery/current observation
before making any SoC-power or battery-life equivalence claim.
